## 本地音乐扫描逻辑梳理
- 应用户要求，全面梳理了 PixelPlayer 本地音乐扫描逻辑
- 架构为**双路径**：
  - 后台同步路径：`SyncWorker` (CoroutineWorker + WorkManager) → MediaStore 查询 → Room 数据库
  - 实时响应路径：`MediaStoreSongRepository` combine 多源 → 直接查 MediaStore → Flow (不落库)
- 调度中心：`SyncManager`，暴露 sync/incrementalSync/fullSync/rebuildDatabase/forceRefresh
- 三种同步模式：INCREMENTAL / FULL / REBUILD
- 核心流水线 doWork：删除检测 → MediaStore 查询 → 目录过滤 → 变更识别 → 并发元数据处理(4并发, TagLib增强) → 写库 → LRC/缓存/云源维护
- 关键文件：
  - `app/src/main/java/com/theveloper/pixelplay/data/worker/SyncWorker.kt` 核心引擎
  - `app/src/main/java/com/theveloper/pixelplay/data/worker/SyncManager.kt` 调度器
  - `app/src/main/java/com/theveloper/pixelplay/data/repository/MediaStoreSongRepository.kt` 实时仓库
  - `app/src/main/java/com/theveloper/pixelplay/utils/MediaStoreSelectionUtils.kt` 查询构建(不依赖 IS_MUSIC, MIDI 豁免)
  - `app/src/main/java/com/theveloper/pixelplay/utils/DirectoryRuleResolver.kt` 目录过滤(最近祖先匹配)
  - `app/src/main/java/com/theveloper/pixelplay/data/observer/MediaStoreObserver.kt` 内容变更监听
- 配置存储于 `UserPreferencesRepository` (DataStore)，含目录白/黑名单、最小时长(默认10s)、艺术家分隔符等

## 修复 AudioMetaUtils native 阻塞导致扫描卡死
- 用户反馈歌曲扫描无法完成
- 根因：`AudioMetaUtils.getAudioMetadata()` 使用 `withTimeout` 包裹 `MediaMetadataRetriever.setDataSource()` 的 native JNI 调用，但协程超时无法中断 JNI 阻塞，导致 `Dispatchers.IO` 线程泄漏耗尽、扫描卡死
- 这与 debug-media-scan-350-freeze.md 记录的 `AudioMetadataReader` 同类 bug，但 `AudioMetaUtils` 此前标记为"暂未修复"
- 在用户触发全量扫描（deepScan=true）时，每首歌都会调用此方法
- **修复方案**：将 `withTimeout { ... }` 替换为专用线程池 `metadataExecutor`（4线程, daemon, MIN_PRIORITY）+ `Future.get(timeout)`，与 `AudioMetadataReader` 修复方式一致
- 修改文件：`app/src/main/java/com/theveloper/pixelplay/utils/AudioMetaUtils.kt`
- 次要风险（暂未修）：`AlbumArtUtils.extractEmbeddedAlbumArtBytesInternal()` 也使用 `MediaMetadataRetrieverPool.withRetriever` 无超时保护，但在 SyncWorker 扫描路径上用的是 `getAlbumArtUriForLibraryScan`（只检查缓存），不受影响；仅在 `MediaStoreSongRepository` 实时路径的首次加载时可能卡单首
